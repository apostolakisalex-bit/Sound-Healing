## TL;DR
The production backend **built, installed, and is running healthy**, and **`POST /api/auth/session` is reachable** (not 404/502/down). The hypothesis that a pip/httpx resolver conflict took the backend down in production is **NOT what happened** — the live backend is up and serving `/api`, currently running with the *unfixed* `httpx==0.27.2`. Therefore the httpx fix, while valid and verified, is **not** the cause of the current Google-login failure. No failing login requests are hitting the backend at all, which points the actual failure **upstream of the backend** (the Emergent OAuth redirect inside Expo Go / the frontend), not at `/api/auth/session`.

## Question 1 — Did the backend build/install succeed and is it running/healthy?
**YES.**
- Active run `ee6d7101` = `success`. A build-step pip failure would have made the run `failed`; it did not.
- Runtime logs (last 120 min) show uvicorn actively serving traffic. The repeated `GET /health … 404` lines are just the K8s probe hitting a path the app doesn't define — the FastAPI process is alive and answering.
- Live probe: `GET /api/auth/session` → **405 Method Not Allowed** with FastAPI JSON body `{"detail":"Method Not Allowed"}`. A 405 (not 404/502) proves the POST route is registered and the backend is up.

### About the pip/httpx conflict
- The conflict is **real on a clean install**. In the eph sandbox: `pip install google-genai==2.2.0 httpx==0.27.2 openai==1.99.9 litellm==1.80.0` → `ERROR: ResolutionImpossible … google-genai 2.2.0 depends on httpx<1.0.0 and >=0.28.1 / user requested httpx==0.27.2`.
- **BUT** the deployed active-run source still pins `httpx==0.27.2` (the claimed fix is NOT in this live run) and the backend is nonetheless running. The base-image/layer-cache build path did not trigger a clean-slate resolver pass, so `ResolutionImpossible` was never hit during the actual production build. Net: the conflict did not bring production down.
- **Fix verification:** `pip install --dry-run google-genai==2.2.0 httpx==0.28.1 openai==1.99.9 litellm==1.80.0` resolves cleanly (`Would install … httpx-0.28.1 … google-genai-2.2.0 …`, no error). The `httpx==0.28.1` change is correct and compatible with openai 1.99.9 / litellm 1.80.0 / google-genai 2.2.0.
- **Recommendation:** ship the `httpx==0.28.1` fix anyway — build hygiene. A future `--clear-cache` / cortex_retry clean rebuild WOULD hit `ResolutionImpossible` with the old pin. It is a latent build risk, just not the current login root cause.

This matches the healthy preview behavior you described.

## Secrets (active run) — all present
`JWT_SECRET` (set, non-empty), `APPLE_AUDIENCES` (set), `REACT_APP_BACKEND_URL` = `https://healing-universe.emergent.host` (correct — this is the value baked into the Expo JS bundle as the backend URL). No missing-secret cause found for the auth path.

## The actual login-failure signal
In 120 minutes of backend logs, the **only** hit to `/api/auth/session` was my own diagnostic GET (405). There are **zero POSTs**, zero 401s, zero 502s, zero tracebacks, zero CORS errors. If Google login were failing *at the backend* (bad session exchange → 401, or outbound failure → 502), we would see POST attempts erroring. We see none. That means the app is **not reaching `/api/auth/session`** — the break is most likely **upstream of the backend**: the Emergent OAuth web-redirect flow inside Expo Go that is supposed to produce the one-time `session_id`, or the frontend not firing/handling the POST. (Caveat: it's also possible no user retried login during this window; but combined with a provably-healthy backend, upstream is the strong candidate.)

CORS note: `allow_origins` comes from `CORS_ORIGINS` (server.py:1174). For a native Expo Go client this is usually irrelevant (native requests aren't browser-CORS-gated), so CORS is unlikely to be the cause for the mobile app.

## What I could NOT verify here
The live OAuth redirect/`session_id` handshake inside Expo Go requires a real device + interactive Google login and is not reproducible in the secret-less sandbox. I could not confirm the exact upstream break.
